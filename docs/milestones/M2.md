## Integrated implementation

The browser workflow is Customer -> Restaurant -> Menu -> Cart -> Checkout ->
Order. `/app/` serves the frontend from the same FastAPI application.

| Capability | Implementation and evidence |
|---|---|
| Registration, sign-in, profile/address changes, deactivation | `app/routes/auth.py`, `app/routes/customers.py`; `tests/test_customer_auth.py`, `tests/test_customer_profile.py`, `tests/browser/account.spec.mjs` |
| Restaurant discovery/search/filter, details, restaurant/menu writes | `app/routes/restaurants.py`, `app/routes/menu.py`; restaurant/menu API tests and `tests/browser/browsing.spec.mjs` |
| Active cart, add/update/remove/clear, backend totals | `app/services/cart_service.py`, `app/repositories/cart_repo.py`; `tests/test_cart_api.py`, `tests/test_cart_add.py`, `tests/test_cart_edit.py` |
| Current-menu revalidation, order snapshot, consume cart only after save | `app/services/checkout_service.py`, `app/repositories/order_repo.py`; `tests/test_checkout.py`, `tests/test_checkout_atomicity.py`, `tests/test_checkout_integrity.py` |
| Order list/detail and history after restart | `app/services/order_service.py`; `tests/test_order_retrieval.py`, `tests/test_m2_integration.py`, `tests/browser/workflow.spec.mjs` |
| Authentication, roles and ownership enforced on backend | `app/core/auth.py`; `tests/test_auth_guards.py`, `tests/test_management_auth.py`, the 28-case role matrix in `tests/test_m2_integration.py` |

Public browsing does not require a token. Restaurant/menu writes require an owner
or admin role. Cart operations and checkout require an active customer acting on
their own cart; admins have no cart bypass. Profile/order reads have their own
admin-access policy. Tokens expire after one hour and are lost on server restart;
sign in again when demonstrating persisted orders.

Prices and totals come from the backend. Checkout reads current menu values,
saves an immutable order snapshot and an internal cart-consumption receipt in
one atomic order write. A failed order write does not consume the cart. Later
menu edits do not rewrite historical orders. See the
[API contract](../API_CONTRACT.md) and [storage decision](../decisions/json-writes.md).

## Reproduce and verify

Follow [README setup](../../README.md#setup), using Python 3.14.7 and Node.js 22
(the CI Node version). Install Python dependencies, run `npm ci`, then install
the Playwright browser with `npx playwright install chromium`. Linux CI uses
`npx playwright install --with-deps chromium`.

```bash
python -m uvicorn app.main:app --reload
# Frontend: http://127.0.0.1:8000/app/
# OpenAPI UI: http://127.0.0.1:8000/docs
# Machine-readable contract: http://127.0.0.1:8000/openapi.json
```

Run from the repository root with the virtual environment active:

```bash
PYTHONWARNDEFAULTENCODING=1 python -m pytest tests -q
npm run test:frontend
npm run test:e2e
git diff --exit-code -- data/
```

On PowerShell, set `$env:PYTHONWARNDEFAULTENCODING = '1'` before running pytest.
Browser fixtures start their own server; a separate development server is not
required. Both Python and browser tests use temporary persistence. Browser tests
also verify that source restaurant, product, customer, cart and order files are
unchanged, including files that were originally absent.

## Fifteen-minute demonstration

Use a separate disposable data directory for the live demo; do not alter
committed representative data. Register a demo customer and a separate management
account. Grant the latter a role using `python -m scripts.set_role EMAIL
restaurant_owner` with the same `FOOD_DELIVERY_DATA_DIR` as the server.

| Time | Demonstration |
|---|---|
| 0-2 minutes | Show the submitted tag/SHA; register or sign in; update customer address; browse/search/filter restaurants and open a menu. |
| 2-5 minutes | Add items, change quantity, remove an item, show backend total; explain one active cart and single-restaurant enforcement. |
| 5-8 minutes | Through `/docs`, attempt cross-restaurant, unavailable-item, invalid-quantity and unauthorized operations; show response and preserved cart. Use a separate customer for deactivation. |
| 8-10 minutes | Change price before checkout; show revalidated order amount, saved snapshot and empty cart; open history/detail. |
| 10-12 minutes | Restart server, sign in again and retrieve the same order; show a representative integration/regression test. |
| 12-15 minutes | Trace route -> service -> repository -> JSON, explain each member's improvement and review evidence, answer TA questions. |

Useful targeted tests:

```bash
python -m pytest tests/test_m2_integration.py -q
python -m pytest tests/test_checkout.py -k 'write_failure or current_menu' -q
npx playwright test tests/browser/workflow.spec.mjs
```

Scope limits: one application process and local JSON storage; no payment processor,
delivery integration or full order lifecycle in M2. Atomic replacement is not a
general cross-file transaction or multi-worker database. See the storage decision
for backup and power-loss limitations.
